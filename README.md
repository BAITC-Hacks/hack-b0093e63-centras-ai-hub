# EKT AI-консультант

ИИ-консультант для интернет-магазина [ekt.kz](https://ekt.kz) (ГК «Электрокомплект»).
Команда **Centras AI HUB** · хакатон BAITC.

> **Главный принцип — точность.** Консультант не «помнит» каталог. Каждый факт (цена, артикул,
> характеристика, адрес, условие возврата) он получает инструментом из базы, собранной с ekt.kz,
> и даёт ссылку на карточку товара. Если данных нет, он прямо говорит об этом и предлагает
> уточнить запрос или оставить заявку менеджеру.

**Проверить за минуту, ничего не устанавливая** (bash / zsh / Git Bash, Node.js ≥ 20):

```bash
node -e 'fetch("https://gqdwplbvxopanapxzlaw.supabase.co/functions/v1/chat",{method:"POST",headers:{"content-type":"application/json"},body:JSON.stringify({message:process.argv[1]})}).then(r=>r.text()).then(t=>console.log(t.split("\n").filter(l=>l.startsWith("data:")).map(l=>JSON.parse(l.slice(5)).text||"").join("")))' "Нужна светодиодная лампа E27, тёплый свет, до 1000 тенге"
```

Ожидаемый ответ: список реальных ламп E27 с тёплым светом дешевле 1000 ₸, у каждой ссылка на
ekt.kz, артикул и цена (на 2026-09-23: LEDVANCE LED A75 2700K, арт. 081100328_, 620 ₸; PHILIPS
Ecohome A60 3000K, арт. 080300163_, 800 ₸). Другие способы проверки описаны в
[разделе 8](#8-как-проверить-решение).

## 1. Название проекта

**EKT AI-консультант**: ИИ-консультант интернет-магазина электротехники ekt.kz с поиском по
каталогу, базой знаний магазина и встраиваемым чат-виджетом.

## 2. Краткое описание

**Проблема.** В каталоге ekt.kz около 14 000 страниц. Покупателю трудно подобрать товар по
характеристикам (цоколь, мощность, цветовая температура), найти цену по артикулу, условия
оплаты и возврата или адрес и график филиала. Сейчас за этим нужно звонить менеджеру. Обычный
чат-бот на LLM в такой задаче выдумывает цены и товары.

**Решение.** Чат-консультант отвечает только по данным, собранным с ekt.kz. Он подбирает
товары по характеристикам и бюджету, называет цену, артикул и ссылку, отвечает на вопросы об
условиях заказа, оплаты и возврата, даёт контакты 9 филиалов и принимает заявку менеджеру.
Цены ежедневно сверяются с сайтом, изменения записываются в историю.

**Для кого.** Для покупателей ekt.kz, розничных и оптовых. Для магазина это меньше звонков
с типовыми вопросами и заявки с уже собранным запросом (что нужно, сколько, телефон, город).

## 3. Что реализовано

В этой версии всё перечисленное ниже работает и проверено на развёрнутом стенде 2026-09-23.

- [x] **Сбор данных с ekt.kz** (`scraper/`): sitemap, robots.txt, разбор HTML кодом (cheerio,
  без LLM). Разбираются карточки товаров, категории, информационные страницы и 9 филиалов.
  Есть режим одной категории (`SCRAPER_CATEGORY`, `SCRAPER_MAX_PRODUCTS`).
- [x] **Загрузка в Supabase** (`npm run ingest`): upsert в схему `ekt`, эмбеддинги
  `text-embedding-3-small` только для новых и изменённых записей, нарезка страниц на фрагменты.
- [x] **Загружены данные**: вся категория «Лампы», 89 товаров, у всех есть цена; 123
  информационные страницы (539 фрагментов с эмбеддингами); 9 филиалов. Снимок от 2026-09-23.
- [x] **Гибридный поиск в Postgres**: точный артикул, полнотекстовый поиск (`russian`),
  триграммы (опечатки) и вектор (pgvector), слияние через Reciprocal Rank Fusion. Фильтры по
  бренду, категории, цене и характеристикам применяются до ранжирования.
- [x] **Чат-консультант** (Supabase Edge Function `chat`, развёрнута): OpenAI `gpt-4.1-mini`
  с вызовом 7 инструментов, потоковый ответ (SSE), история диалога, ответы на русском,
  казахском и английском, отказ от посторонних тем, защита от prompt injection.
- [x] **Защита от выдумок**: детерминированная постпроверка `validate.ts` сверяет ссылки на
  ekt.kz и цены в ответе с результатами инструментов и пишет расхождения в
  `chat_messages.flags`. Карточки товаров показываются только для товаров, которые вернули
  инструменты. Сообщение не в UTF-8 отклоняется с кодом 400. На непонятное сообщение
  консультант просит переформулировать, а не угадывает.
- [x] **Заявка менеджеру** (`create_lead`): создаётся только после явного согласия клиента и
  с его телефоном. Хранится в `ekt.leads`, не больше 3 заявок на сессию.
- [x] **Отслеживание цен**: `ingest` сравнивает свежие цены с базой, пишет изменения в
  `ekt.price_history`, помечает товар (`price_site_prev`, `price_changed_at`) и печатает
  сводку. Консультант может сказать «цена изменилась с X ₸ на Y ₸», но только если это
  есть в данных. Работа проверена на живой базе: цену подменили в БД, `npm run ingest`
  обнаружил изменение и записал историю.
- [x] **Ежедневное обновление**: workflow GitHub Actions `refresh-data.yml` (03:15 по Алматы)
  с проверкой цен категории. Workflow написан, но секреты репозитория ещё не заданы (см.
  [ограничения](#10-ограничения)).
- [x] **Встраиваемый виджет** (`web/`): один `<script>` без зависимостей, 38.5 KB (14.5 KB
  gzip, лимит сборки 40 KB), Shadow DOM,
  потоковые ответы, карточки товаров, оценки 👍/👎, клавиатура, мобильная вёрстка.
  Собран и проверен командой в headless Chrome. Запускается локально, на Vercel ещё не
  опубликован.
- [x] **Воспроизводимость**: снимок данных в `seed/`, локальный стек одной командой
  `npm run setup:local` (Docker), дымовой тест `npm run smoke`, eval-набор `npm run eval`.
- [x] **Тесты и CI**: `npm test` (vitest, 113 тестов: парсеры на HTML-фикстурах ekt.kz,
  нарезка, сравнение цен, markdown и SSE виджета), `deno test` функции чата (94 теста: HTTP,
  OpenAI-клиент, промпт, SSE, инструменты, постпроверка `validate.ts`, вспомогательные
  функции UI-действий виджета), GitHub Actions `ci.yml`.

## 4. Как работает решение

Основной сценарий, от вопроса покупателя до ответа:

1. **Вход.** Покупатель пишет в виджете на странице (или шлёт `POST /functions/v1/chat`):
   «Нужна светодиодная лампа E27, тёплый свет, до 1000 тенге». Виджет передаёт `message`,
   `session_id`, адрес текущей страницы и город, если он задан (`data-city`).
2. **Проверки.** Edge Function проверяет CORS, UTF-8, длину (не больше 2000 символов) и
   rate-limit (20 сообщений в минуту на сессию, 60 на IP). Затем создаёт или продолжает
   сессию в `ekt.chat_sessions` и отправляет событие `session`.
3. **Выбор инструмента.** В OpenAI уходят системный промпт с правилами точности, последние 12
   сообщений диалога и описание 7 инструментов. Модель решает, что вызвать, в этом примере
   `search_products` с фильтрами (цоколь E27, цена до 1000). Виджет показывает статус
   «Ищу товары…».
4. **Поиск.** Функция считает эмбеддинг запроса и вызывает RPC `ekt.search_products`
   (гибридный поиск в Postgres). Модель получает найденные товары с ценами, артикулами,
   ссылками, характеристиками и датой обновления данных. Для вопросов об условиях вызывается
   `search_knowledge`, о филиалах `get_branches`. За ответ допускается не больше 5 раундов
   инструментов.
5. **Ответ.** Модель пишет ответ только из полученных данных. Текст приходит потоком
   (события `delta`), затем событие `products` с карточками найденных товаров.
6. **Постпроверка.** `validate.ts` сверяет все ссылки на ekt.kz и все цены в ответе с
   результатами инструментов. Расхождения записываются во `flags`, ответ и вызовы
   инструментов сохраняются в `ekt.chat_messages`. Событие `done` передаёт `message_id`
   для оценки 👍/👎.
7. **Результат.** Покупатель видит 1–5 товаров со ссылками на ekt.kz, артикулами и ценами,
   карточки товаров и строку «цены актуальны на дату обновления, наличие уточняет
   менеджер». Если нужен расчёт или опт, консультант предлагает оставить заявку.

## 5. Технологии

| Слой | Технология | Почему |
|---|---|---|
| Языки | TypeScript (скрапер, виджет, функция чата), SQL (PL/pgSQL-миграции), JavaScript (служебные скрипты `scripts/*.mjs`) | |
| БД | Supabase Postgres 15 + `pgvector` + `pg_trgm` + полнотекстовый поиск `russian` | один сервис для данных, поиска и логов; гибридный поиск в SQL |
| Бэкенд чата | Supabase Edge Functions (Deno) | рядом с БД, без своих серверов, стриминг SSE |
| LLM | OpenAI Chat Completions + tool calling (`OPENAI_MODEL`, по умолчанию `gpt-4.1-mini`) | модель задаётся переменной, меняется без правки кода |
| Эмбеддинги | OpenAI `text-embedding-3-small` (1536) | хорошее качество на русском, ≈ $0.04 за полный каталог |
| Скрапер | Node.js 20+, TypeScript (`tsx`), `cheerio`, `dotenv` | быстрый парсинг, запуск локально и в GitHub Actions |
| Клиент БД | `@supabase/supabase-js` | ingest и функция чата |
| Виджет | TypeScript без зависимостей, esbuild, Shadow DOM | не конфликтует со стилями ekt.kz, < 40 KB |
| Тесты | vitest (Node), `deno test` (функция чата) | |
| Хостинг фронта | Vercel (статический `web/public`, конфиг `vercel.json`); **пока не задеплоен** | CDN для `widget.js` и демо-страницы |
| CI/CD | GitHub Actions | тесты и ежедневное обновление данных |
| Локальный стек | Supabase CLI (dev-зависимость, `npx supabase`) + Docker | запуск без облачных ключей команды |

Внешние сервисы: **OpenAI API** (чат и эмбеддинги), **Supabase** (Postgres, Data API, Edge
Functions), **GitHub Actions**, **Vercel** (подготовлен, не опубликован), **ekt.kz** как
источник данных (подробнее в [разделе 9](#9-данные-и-интеграции)).

## 6. Архитектура проекта

```
            ┌──────────── ежедневно 03:15 (GitHub Actions) ────────────┐
            │                                                           ▼
ekt.kz ──► scraper (Node/TS) ──► data/*.jsonl ──► ingest ──► Supabase Postgres, схема ekt
 sitemap    robots.txt, 3–4 потока      │           │         ├─ products (цены, характеристики, pgvector)
 ~14 000    парсинг HTML без LLM        │           │         ├─ price_history (изменения цен)
 URL                                    │           │         ├─ categories, branches
                     seed/*.jsonl ──────┘           └─ OpenAI embeddings (только изменённое)
                     (снимок в git)                           ├─ pages / page_chunks (FAQ, условия, статьи)
                                                              └─ chat_sessions / messages / leads / feedback
                                                                    ▲
Покупатель на ekt.kz                                                │ RPC: гибридный поиск
   └─ widget.js ──SSE──► Edge Function `chat` ──► OpenAI GPT + 7 tools
```

Компоненты и их взаимодействие:

1. **Скрапер** (`scraper/src/scrape.ts`) обходит `sitemap.xml` ekt.kz и разбирает HTML
   обычным кодом (cheerio). LLM для скрапинга не используется: это бесплатно и
   детерминированно. Результат пишется в `data/*.jsonl`.
2. **Ingest** (`scraper/src/ingest.ts`) загружает `data/` (или `seed/` с флагом `--dir seed`)
   в Supabase, находит изменения цен и считает эмбеддинги только для новых и изменённых
   записей.
3. **Supabase Postgres** (схема `ekt`) хранит каталог, базу знаний, филиалы, историю цен,
   диалоги и заявки. Поиск реализован RPC-функциями в SQL. RLS закрывает таблицы от
   публичного доступа.
4. **Edge Function `chat`** (`supabase/functions/chat/`) ведёт диалог. Модель GPT вызывает
   инструменты (поиск товаров, карточка, характеристики категории, категории, база знаний,
   филиалы, заявка), отвечает потоком (SSE), постпроверка сверяет ссылки и цены.
5. **Виджет** (`web/`) подключается одним `<script>` на сайте: кнопка чата, потоковые
   ответы, карточки товаров, оценки 👍/👎.
6. **GitHub Actions**: `ci.yml` (тесты, сборка виджета, `deno check` и `deno test`) и
   `refresh-data.yml` (ежедневный scrape, ingest и сводка изменений цен).

## 7. Установка и запуск

Есть три пути. **Путь A** ничего не требует ставить. **Путь B** поднимает всё локально из
чистого клона с данными из `seed/`. **Путь C** разворачивает решение в своём облачном
проекте Supabase.

> Во всех путях ниже используется `npm ci` (чистая установка строго по `package-lock.json`,
> как в CI). На момент проверки README (см. [журнал верификации](docs/README-VERIFICATION.md))
> `npm ci` на чистом клоне текущей ветки завершался ошибкой `npm error Missing: ... from lock
> file` — `package-lock.json` временно разошёлся с `package.json` (в процессе добавления
> Chrome-расширения). Если увидите эту ошибку, используйте `npm install` — он ставит те же
> зависимости и все команды ниже (`npm test`, `npm run build:web` и т. д.) после него работают
> штатно. `npm ci` — целевая команда для CI и для установки без сюрпризов, когда lock-файл
> синхронизирован; лечится обычным `npm install` с последующим коммитом обновлённого
> `package-lock.json`.

### Путь A: развёрнутая версия

API уже работает. Ключ не нужен. Адреса перечислены в
[разделе 11](#11-ссылка-на-deployed-версию).

```bash
# проверка доступности (в браузере или терминале)
curl https://gqdwplbvxopanapxzlaw.supabase.co/functions/v1/chat/health
# → {"ok":true,"db":true,"openai_key":true,"model":"gpt-4.1-mini",...}
```

Вопрос консультанту: Node-однострочник из [начала README](#ekt-ai-консультант) или
`npm run smoke` (см. [8.2](#82-дымовой-тест-npm-run-smoke)). Виджет с развёрнутым API
(нужен клон репозитория и Node.js ≥ 20):

```bash
npm ci
npm run dev:web
# открыть http://localhost:5173/?api=https://gqdwplbvxopanapxzlaw.supabase.co/functions/v1/chat
```

> На Windows запросы с кириллицей лучше слать через Node (`npm run smoke`, однострочник выше
> в Git Bash) или через виджет. `curl` в Git Bash может испортить кодировку тела, и тогда
> функция вернёт 400 «message must be UTF-8 encoded».

### Путь B: локально из репозитория (Supabase в Docker, данные из `seed/`)

Требования: Node.js ≥ 20, запущенный **Docker Desktop** (или совместимый движок), свой
`OPENAI_API_KEY`. Аккаунт Supabase не нужен: Supabase CLI ставится как dev-зависимость.

```bash
git clone <url-репозитория> && cd <папка>
npm ci
cp .env.example .env.local          # PowerShell: Copy-Item .env.example .env.local
# в .env.local заполнить OPENAI_API_KEY=sk-...
# SUPABASE_* для локального запуска заполнять не нужно

npm run setup:local
```

`npm run setup:local` (`scripts/setup-local.mjs`) выполняет по шагам:

1. `docker info`: если Docker не запущен, скрипт останавливается с понятной ошибкой;
2. `npx supabase start` поднимает локальный стек (первый запуск скачивает образы
   Supabase, это занимает несколько минут);
3. `npx supabase db reset --local` применяет миграции `supabase/migrations/*`;
4. `npx supabase status -o env` берёт локальные URL и ключи и пишет их в
   `.env.local.generated` (файл `.env.local` скрипт не меняет);
5. `ingest --dir seed` загружает снимок (89 товаров, 123 страницы, 9 филиалов) в локальную
   БД. Без `OPENAI_API_KEY` загрузка идёт с `--no-embed`: векторный поиск отключён,
   текстовый и по артикулу работает.

Затем в двух терминалах:

```bash
npm run serve:fn     # supabase functions serve chat --no-verify-jwt --env-file .env.local
npm run dev:web      # сборка виджета + http://localhost:5173
```

Открыть: `http://localhost:5173/?api=http://127.0.0.1:54321/functions/v1/chat`.
Supabase Studio (таблицы `ekt.*`): `http://127.0.0.1:54323`.
Дымовой тест локальной функции:
`CHAT_URL=http://127.0.0.1:54321/functions/v1/chat npm run smoke`.

Повторно загрузить seed (например, после того как появился ключ OpenAI) можно командой
`npm run ingest:seed` с `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` из

## 9. Данные и интеграции

### Источник и состав

Единственный источник данных — публичный сайт [ekt.kz](https://ekt.kz). Снимок от
**2026-09-23**, он же загружен в развёрнутую базу:

| Данные | Объём | Откуда |
|---|---|---|
| Товары категории «Лампы» (`/catalog/svetilniki_lampy/lampy/`) | **89**, вся категория, у всех есть цена | карточки товаров: название, Bitrix ID, артикул, артикул поставщика, бренд, цена на сайте и в магазине, кратность, все характеристики, описание, фото, путь категории |
| Категории | 24 | путь до корня для каждой категории товаров |
| Информационные страницы | 123 → 539 фрагментов с эмбеддингами | FAQ, как заказать, оплата, возврат и обмен, о компании, производство, торговые марки, статьи, техническая информация, новости |
| Филиалы | 9 | страница контактов: город, адрес, телефоны, email, график |

Снимок лежит в [`seed/`](seed/README.md) (`products.jsonl`, `categories.jsonl`, `pages.jsonl`,
`branches.json`, `scrape-report.json`). Из него собирается локальный стек и загружается любой
свой проект Supabase, без обращения к ekt.kz.

**Почему одна категория.** Сайт-источник отвечает медленно: временами 7–30 секунд на
страницу. Полный обход около 14 000 URL из sitemap по оценке занимает 12–15 часов. Команда
выбрала глубину, а не ширину: консультант полностью знает одну категорию (все товары, цены,
характеристики) и все условия магазина. Скрапер и схема рассчитаны на весь каталог.
Переключиться на другую категорию или весь каталог можно переменными `SCRAPER_CATEGORY` и
`SCRAPER_MAX_PRODUCTS` (без `SCRAPER_CATEGORY` скрапер обходит весь каталог).

**Что известно о данных сайта.** Остатков на складе в карточках ekt.kz нет, поэтому
консультант не обещает наличие. Цены не зависят от города: 5 товаров сверили в Алматы и
Астане, цены совпали. В ответах консультант пишет «цены для Алматы» (Алматы — город сайта по
умолчанию). У части товаров сайта вместо цены стоит «Под заказ». Такая пометка хранится в
`order_note`, и консультант не называет для этих товаров цену. В загруженной категории
«Лампы» таких товаров нет.

## 10. Ограничения

Текущее состояние на 2026-09-23:

1. **Одна категория товаров.** В базе только «Лампы» (89 товаров), плюс все информационные
   страницы и филиалы. На вопросы о других товарах (автоматы, кабель, розетки) консультант
   отвечает, что не нашёл, и предлагает уточнить запрос или оставить заявку. Товары из других
   категорий он не придумывает. Такие ответы бывают неуклюжими (например, «выведены лампы»).
   Две из шести кнопок-примеров на демо-странице (`web/public/index.html`: автомат 25А,
   кабель ВВГнг) относятся к незагруженным категориям.
2. **Нет остатков.** На сайте нет информации о наличии, поэтому консультант не обещает ни
   наличие, ни сроки. Их уточняет менеджер.
3. **Цены на дату снимка.** Данные от 2026-09-23. Независимость цены от города проверена
   выборочно (5 товаров, Алматы и Астана), а не на всех товарах.
4. **Ежедневное обновление пока не запущено.** Workflow `refresh-data.yml` готов, и логика
   сравнения цен проверена на живой базе. Но в GitHub-репозитории ещё не заданы секреты
   `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `OPENAI_API_KEY`, поэтому ночной запуск пока
   упадёт. До этого данные обновляются вручную: `npm run refresh` с `SCRAPER_CATEGORY`.
5. **Медленный сайт-источник.** До 7–30 с на страницу, полный каталог займёт 12–15 часов.
   Для ежедневного прогона это приемлемо только в режиме одной категории.
6. **Режим одной категории и деактивация.** `ingest` помечает неактивными товары, которых нет
   в полном прогоне, а прогон по категории тоже считается полным. Если в базу когда-нибудь
   загрузят весь каталог, ежедневный прогон по одной категории деактивирует остальные товары.
   Сейчас база состоит из одной категории, и проблема не проявляется.
7. **Виджет не опубликован.** Vercel-деплой не сделан (нет токена), на ekt.kz виджет не
   встроен. Виджет запускается локально (`npm run dev:web`) с развёрнутым API. Проверку в
   браузере команда делала в headless Chrome.
8. **`npm run setup:local` не прогнан командой полностью.** На машине разработчика не было
   Docker. Проверены: остановка с понятной ошибкой без Docker, разбор
   `supabase status -o env`, `ingest --dry-run --dir seed` (89 товаров, 539 фрагментов). Те же
   файлы ingest загрузил в развёрнутую облачную базу. Шаги
   `supabase start` → `db reset` → локальный ingest → `serve:fn` реализованы по документации
   Supabase CLI, но целиком не запускались.
9. **Качество ответов LLM не гарантировано на 100 %.** Модель недетерминирована. Процент
   прохождения eval смотрите в [`eval/RESULTS.md`](eval/RESULTS.md). Постпроверка
   `validate.ts` только **помечает** подозрительные ссылки и цены во `flags`, а ответ
   клиенту не блокирует и не исправляет.
10. **Язык ответа.** Правило «отвечать на языке клиента» есть в промпте. Но в нашей проверке
    на вопрос на казахском консультант подобрал верные товары и ответил по-русски.
11. **Заявки никуда не отправляются.** Заявка сохраняется в `ekt.leads`. Уведомлений
    менеджерам (email, мессенджер) нет, заявки просматриваются SQL-запросом в Supabase
    Studio.
12. **Доступ из браузера ограничен CORS.** Развёрнутый API принимает браузерные запросы только
    с `ekt.kz` и `http://localhost:5173`, с других доменов будет 403. Запросы без заголовка
    `Origin` (Node, curl) проходят. Действуют rate-limit: 20 сообщений в минуту на сессию и
    60 на IP.

AND — иначе «10 Вт» не находило товар с атрибутом «10»), [`20260923170000_search_rank.sql`](supabase/migrations/20260923170000_search_rank.sql)
(полнотекст участвует в RRF дважды — AND-вариант весом 2.0 поднимает точные совпадения по
всем словам запроса наверх, OR-вариант весом 1.0 сохраняет recall из предыдущей миграции).

Все объекты консультанта лежат в **отдельной схеме `ekt`**. Проект Supabase может быть общим с
другими приложениями, и схема гарантирует, что таблицы и права не пересекаются. Схема `ekt`
добавлена в Data API → Exposed schemas (локально это `[api] schemas` в `supabase/config.toml`).
Клиенты создаются с `db: { schema: "ekt" }`.

| Таблица | Что хранит |
|---|---|
| `categories` | дерево каталога: `url`, `name`, `parent_url`, `path[]`, `depth`, `product_count` |
| `products` | товар: Bitrix `id`, `sku` (артикул), `name`, `url`, `brand`, `price_site` / `price_store` (₸), `order_note` («Под заказ»), `price_site_prev` / `price_store_prev` / `price_changed_at` (последнее изменение цены), `multiplicity`, `attrs jsonb` (все характеристики), `description`, `image_url`, `fts` (tsvector), `embedding vector(1536)`, `content_hash`/`embedded_hash`, `is_active`, `scraped_at` |
| `price_history` | каждое изменение цены: `product_id`, `run_id`, старая и новая цена сайта и магазина, `changed_at` |
| `pages`, `page_chunks` | база знаний: FAQ, как заказать, оплата, возврат, контакты, о компании, производство, статьи, новости; нарезана на фрагменты с эмбеддингами |
| `branches` | 9 филиалов: город, адрес, телефоны, email, график |
| `chat_sessions`, `chat_messages` | диалоги: реплики, вызовы инструментов, токены, задержка, флаги проверки |
| `leads` | заявки менеджерам (имя, телефон, город, запрос, товары, статус) |
| `feedback` | оценки ответов 👍/👎 |
| `scrape_runs` | журнал обновлений данных (включая `stats.price_changes`) |

RPC-функции:

- `search_products(q, q_embedding, p_brand, p_category, p_price_min, p_price_max, p_attrs, p_limit)`:
  гибридный поиск. Точный артикул (вес ×3), полнотекстовый поиск, триграммы (опечатки) и
  вектор сливаются через Reciprocal Rank Fusion. Фильтры применяются до ранжирования. Без
  текста запроса результат сортируется по цене.
- `search_chunks(q, q_embedding, p_kinds, p_limit)`: гибридный поиск по базе знаний.
- `category_facets(p_category)`: какие характеристики и значения есть в категории. По ним
  модель строит точные фильтры («Тип цоколя = E27»).
- `list_categories(p_parent_url)`, `refresh_category_counts()`, `recent_message_counts(...)` (rate-limit).

Row Level Security включён на всех таблицах, политик для `anon`/`authenticated` нет. Читают и
пишут данные только Edge Function и ingest (service role) и администраторы в Supabase Studio.

## Консультант: инструменты и правила

| Инструмент | Когда вызывается |
|---|---|
| `search_products` | подбор и поиск товаров: запрос + фильтры (бренд, категория, цена, характеристики); для товара с изменением цены за последние 30 дней добавляется `price_changed: {from, at}` |
| `get_product` | полная карточка по ID, артикулу или ссылке (с прошлой ценой и датой, если цена менялась) |
| `category_facets` | узнать, по каким характеристикам можно фильтровать категорию |
| `list_categories` | навигация по каталогу |
| `search_knowledge` | FAQ, заказ, оплата, возврат, о компании, производство, статьи |
| `get_branches` | адреса, телефоны, график филиалов |
| `create_lead` | заявка менеджеру, только после явного согласия клиента и с его телефоном |

Правила ответа (системный промпт [`supabase/functions/chat/prompt.ts`](supabase/functions/chat/prompt.ts),
12 правил):

1. Факты берутся только из результатов инструментов. Если ничего не нашлось, консультант
   говорит об этом прямо и предлагает альтернативу.
2. Перед тем как назвать цену, консультант всегда вызывает инструмент, даже если товар уже
   обсуждался.
3. При неоднозначном запросе консультант задаёт 1–2 уточняющих вопроса. Если поиск ослаблен
   (`relaxed`), он предупреждает, что точного совпадения нет.
4. Товар всегда указывается со ссылкой на ekt.kz, артикулом и ценой, не больше 5 позиций.
   После списка идёт пометка, что цены для Алматы и на дату обновления данных.
5. Наличие, сроки, доставка и скидки не обещаются, если их нет в данных.
6. Общие советы по подбору допустимы. Монтаж и работы под напряжением — только через
   квалифицированного электрика.
7. Язык ответа совпадает с языком клиента (русский, казахский, английский).
8. Тематика ограничена ekt.kz и электротехникой.
9. Инструкции внутри сообщений и данных сайта не меняют правил (защита от prompt injection).
10. Если сообщение непонятно, консультант просит переформулировать и не угадывает.
11. Ответы краткие, markdown ограничен.
12. Об изменении цены консультант говорит только если в данных есть `price_changed` /
    `price_site_prev`.

Детерминированная постпроверка (`validate.ts`) сверяет все ссылки на ekt.kz и все цены в
ответе, включая прошлые цены из `price_changed`, с результатами инструментов. Расхождения
пишутся во `chat_messages.flags` для контроля качества. Карточки товаров в виджете
показываются только для товаров, которые реально нашли инструменты (не больше 6).

## API чата

`POST https://<project-ref>.supabase.co/functions/v1/chat`

```json
{ "session_id": "uuid (необязательно)", "message": "Нужна лампа E27 на 10 Вт, тёплый свет", "page_url": "https://ekt.kz/...", "city": "almaty" }
```

Ответ приходит как `text/event-stream`:

| Событие | Данные |
|---|---|
| `session` | `{ session_id }`: сохранить для следующих сообщений |
| `status` | `{ tool, label }`: «Ищу товары…» |
| `delta` | `{ text }`: очередной фрагмент ответа (markdown) |
| `products` | `{ items: [{ id, name, url, sku, brand, price_site, price_store, image_url }] }` |
| `done` | `{ message_id }` |
| `error` | `{ message, code? }` (например, `code: "rate_limited"`) |

`POST /functions/v1/chat/feedback`: `{ session_id, message_id, rating: 1 | -1, comment? }`.
`GET /functions/v1/chat/health`: проверка доступности (БД, наличие ключа OpenAI, модель).

Ограничения: сообщение не длиннее 2000 символов и в UTF-8, иначе 400. Лимиты: 20 сообщений в
минуту на сессию и 60 на IP. В контекст уходят последние 12 сообщений. На ответ допускается
до 5 раундов инструментов. CORS разрешён только доменам из `ALLOWED_ORIGINS`, с других
доменов будет 403.

## Сбор данных с ekt.kz

```bash
npm run scrape                 # полный обход (~14 000 URL; при медленном сайте — 12–15 часов)
npm run scrape -- --resume     # продолжить прерванный обход
SCRAPER_CATEGORY=/catalog/svetilniki_lampy/lampy/ SCRAPER_MAX_PRODUCTS=100 npm run scrape   # одна категория
SCRAPER_LIMIT=100 npm run scrape   # быстрый пробный прогон
npm run ingest                 # загрузить в Supabase + эмбеддинги изменённого + изменения цен
npm run ingest -- --dry-run    # только проверить файлы, без БД
npm run ingest -- --no-embed   # без эмбеддингов
npm run ingest -- --dir seed   # загрузить из другой папки (то же, что npm run ingest:seed)
npm run seed:update            # скопировать data/* в seed/ (обновить снимок)
```

Правила обхода:

- соблюдается `robots.txt`, URL с параметрами (`?…`) не запрашиваются;
- **исключение**: 4 служебные страницы (`/about/faq/`, `/about/howto/`, `/payments/`, `/return/`).
  Они закрыты в `robots.txt` для поисковиков, но нужны консультанту. Сбор этих страниц
  выключается переменной `SCRAPER_SKIP_SERVICE_PAGES=1`;
- 3 параллельных потока по умолчанию (`SCRAPER_CONCURRENCY`, в ежедневном прогоне 4), пауза
  300 мс, таймаут 60 с (`SCRAPER_TIMEOUT_MS`), 3 повтора с экспоненциальной задержкой, свой
  User-Agent `EKT-Consultant-Bot/1.0`;
- в режиме одной категории (`SCRAPER_CATEGORY`) обходятся все некаталожные страницы и
  каталожные URL этой категории. Уже отслеживаемые товары (из базы или из
  `seed/products.jsonl`) идут первыми, остальные добираются до лимита
  `SCRAPER_MAX_PRODUCTS`;
- если обработано меньше 90 % URL или задан `SCRAPER_LIMIT`, товары не деактивируются (защита
  от частичного сбоя).

Ограничения данных сайта: **остатков на складе в карточках нет**, поэтому консультант не
обещает наличие. Цены на сайте одинаковы для городов (выборочная проверка Алматы и Астаны),
по умолчанию сайт показывает Алматы.

## Ежедневное обновление и отслеживание цен

Workflow [`refresh-data.yml`](.github/workflows/refresh-data.yml):

- запускается по расписанию `15 22 * * *` (22:15 UTC, то есть 03:15 по Алматы) и вручную
  (`workflow_dispatch`, параметр `limit`);
- шаги: `npm ci` → `npm test` → `npm run scrape` → `npm run ingest` → артефакт
  `scrape-report`;
- следит за категорией «Лампы»: `SCRAPER_CATEGORY=/catalog/svetilniki_lampy/lampy/`,
  `SCRAPER_MAX_PRODUCTS=100`, 4 потока. Полный обход каталога остаётся ручным;
- требует секреты репозитория `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `OPENAI_API_KEY`.
  **Сейчас они не заданы** (см. [ограничения](#10-ограничения)).

Как отслеживаются цены (`scraper/src/ingest.ts`, `rows.ts: detectPriceChanges`):

1. Перед upsert ingest читает текущие `price_site` / `price_store` из базы и сравнивает их
   со свежими, как числа (`"299.00"` = `299`, переход `null` ↔ число тоже считается
   изменением). Новые товары изменением не считаются.
2. У изменившегося товара в `price_site_prev` / `price_store_prev` записывается старая цена,
   в `price_changed_at` время изменения. У неизменившихся товаров эти поля сохраняются.
3. Каждое изменение пишется строкой в `ekt.price_history` с `run_id` прогона. Первые 50
   изменений попадают в `scrape_runs.stats.price_changes`.
4. В консоль выводится `[ingest] изменения цен: N` и строки вида
   `Товар: сайт 1300 → 1270 ₸`. В GitHub Actions в Job Summary добавляется таблица
   изменений или строка «Изменений цен нет.».
5. Консультант видит изменение. `search_products` добавляет `price_changed` для изменений за
   последние 30 дней, `get_product` возвращает прошлые цены и дату. По правилу 12 промпта
   консультант может сказать «цена изменилась с X ₸ на Y ₸ (дата)».

Проверено 2026-09-23 на развёрнутой базе. Цену товара вручную изменили в БД, после чего
`npm run ingest` вывел «изменения цен: 1 … сайт 1 → 1270 ₸», записал строку в
`ekt.price_history` и заполнил `price_site_prev` / `price_changed_at`. Тестовые изменения
затем удалены.

## Эксплуатация

Полезные запросы в Supabase Studio → SQL:

```sql
-- новые заявки
select * from ekt.leads where status = 'new' order by created_at desc;

-- ответы с подозрением на выдумку (ссылки/цены не из базы)
select session_id, content, flags from ekt.chat_messages
where role = 'assistant' and flags ?| array['unknown_urls','unmatched_prices'] order by created_at desc;

-- дизлайки
select m.content, f.comment from ekt.feedback f join ekt.chat_messages m on m.id = f.message_id
where f.rating = -1 order by f.created_at desc;

-- последние изменения цен
select p.name, h.price_site_old, h.price_site_new, h.changed_at
from ekt.price_history h join ekt.products p on p.id = h.product_id
order by h.changed_at desc limit 20;

-- последние обновления данных
select * from ekt.scrape_runs order by started_at desc limit 5;
```

Сменить модель можно без передеплоя кода: `npx supabase secrets set OPENAI_MODEL=<модель>`.

Переменные Edge Function:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `OPENAI_API_KEY` | — | ключ OpenAI (обязательно) |
| `OPENAI_MODEL` | `gpt-4.1-mini` | модель консультанта |
| `OPENAI_EMBEDDING_MODEL` | `text-embedding-3-small` | эмбеддинги запросов (должна совпадать с ingest) |
| `OPENAI_BASE_URL` | `https://api.openai.com/v1` | прокси / совместимый API |
| `OPENAI_MAX_COMPLETION_TOKENS` | `3000` | лимит длины ответа |
| `ALLOWED_ORIGINS` | `*` | домены виджета через запятую (на развёрнутой версии: ekt.kz и localhost:5173) |

`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` Supabase подставляет в функцию автоматически.
Переменные скрапера и ingest описаны в [`.env.example`](.env.example).

## Безопасность и приватность

- Ключи OpenAI и service role хранятся только в секретах Supabase / GitHub и в локальном
  `.env.local` (он в `.gitignore`), в браузер не попадают.
- В `chat_sessions` хранится хэш IP (SHA-256 от IP вместе с URL проекта), а не сам IP.
- Персональные данные (имя, телефон) хранятся только в `leads`, по явному согласию клиента
  в диалоге.
- RLS закрывает все таблицы от публичного доступа, права выданы только `service_role`.
- Виджет рендерит markdown безопасно: HTML экранируется, ссылки допускаются только
  http/https.
- Текст клиента и страниц сайта считается данными, а не командами. Системный промпт не
  раскрывается (в eval есть сценарии на prompt injection).
