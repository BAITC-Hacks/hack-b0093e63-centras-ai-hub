### 4.1. Риск при загрузке нескольких категорий

**Что есть сейчас.** Скрапер умеет собирать одну категорию. Но `ingest.ts:207` считает прогон полным по `!report.limit`, а затем `:337` выбирает для деактивации все активные товары БД, которых нет в загружаемом наборе. Область категории в этом решении не учитывается.

**Как это проявится.** В базе есть лампы и кабели. Выполняется обновление только ламп или повторная загрузка `seed/`. Кабели отсутствуют в этом наборе и могут получить `is_active=false`, после чего исчезнут из поиска. Это не физическое удаление строк, но пользователь перестанет находить эти товары.

**Чем подтверждено.** [Dry-run](../evidence/ingest-dry-run.txt) на 89 товарах вывел `full_run: true` и `will_deactivate_missing: true`. База при проверке не изменялась. Факта потери товаров на работающем стенде не установлено.

**Минимальное исправление.** Передавать в отчёте явную область обхода и разрешать общую деактивацию только после полного обхода. Для частичного снимка отключить её либо ограничить подтверждённой категорией. Проверить на базе с двумя категориями: после обновления одной вторая остаётся активной; реально исчезнувший товар внутри проверенной области обрабатывается ожидаемо.

## 5. Наблюдения вне шкалы и условия реального внедрения

Эти пункты не используются как новые основания снижения баллов.
